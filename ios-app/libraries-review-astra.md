The additions should stay small: clocks and clearer build output first, then targeted test/performance work. Clocks and Concurrency Extras are already dependencies of the current [swift-dependencies manifest](https://github.com/pointfreeco/swift-dependencies/blob/main/Package.swift); inspect the resolved version before adding redundant declarations or attributing savings twice. Concurrency Extras explicitly warns that its serial executor uses mutable global runtime state: isolate tests using it from concurrently running tests and retain other coverage for real concurrency. [Concurrency Extras documentation](https://github.com/pointfreeco/swift-concurrency-extras#serial-execution).

The bigger missing investment is a testable boundary around Apple frameworks, not another framework wrapper. My recommended fixtures are recorded pose landmarks with tolerances and orientation cases; interrupted/restarted recording sequences; location and authorization transitions; duplicate and out-of-order sync events; and replay retention under a fixed memory/disk budget. Exercise these with Swift Testing on the Mac, then use a small device matrix to check real permissions, capture, inference, background behavior, and watch connectivity. Do not assume iCloud Documents sync is CloudKit record sync: establish which mechanism each app uses before recommending a sync package or persistence migration.

Also add accessibility checks even if the snapshot package is deferred: Apple's [XCTest accessibility audit](<https://developer.apple.com/documentation/xcuiautomation/xcuiapplication/performaccessibilityaudit(for:_:)>) supplies an existing tool, followed by targeted VoiceOver and Dynamic Type checks. These are complementary to Maestro flows.

## 2. What I would demote, replace, or promote

**Fastlane: demote from top-three adoption to a targeted signing/release experiment.** `match` distributes certificates, private keys, and provisioning profiles. It can reduce reliance on interactive Xcode account state, but cannot promise to end authentication, entitlement, expired-profile, or device-registration failures. First classify an actual failed deploy from its logs. Adopt `match` only if reproducible signing-material installation fixes that failure. It can sit beside `xcodebuild` and `devicectl`; replacing that working loop is unnecessary. [match documentation](https://docs.fastlane.tools/actions/match/).

**SnapshotTesting: retain, but demote broad UI snapshots from “biggest win” to a small pilot.** Start with host snapshots of stable report schemas, serialized fixtures, and presentation values. Add a handful of UI states with reviewed references. Pin simulator runtime, rendering configuration, locale, appearance, and fonts; image comparisons do not certify that the initial image is correct. iOS rendering belongs on the simulator rung, while value snapshots can run on the Mac. [SnapshotTesting documentation](https://github.com/pointfreeco/swift-snapshot-testing).

**swift-dependencies: retain as a strong candidate, not a prerequisite for host tests.** Plain initializer-injected clients and clocks may be enough. The value comes from extracting logic and controlling side effects; this library makes that consistent across features. It does not provide a ready-made HealthKit client or make iOS-only code compile on macOS. Use it independently of TCA where it pays for itself. [swift-dependencies](https://github.com/pointfreeco/swift-dependencies).

**swift-collections: promote when replacing an actual queue or ordered-index implementation.** Replay and breadcrumb buffers are unusually good matches. However, a ring-buffer-backed `Deque` is not automatically a bounded, overwriting, thread-safe video recorder. Igor still owns eviction, resource lifetime, synchronization, and memory budgets. Current releases also offer `RigidDeque`, with different constraints and toolchain requirements; select the smallest compatible API. [Collections](https://github.com/apple/swift-collections), [RigidDeque](https://github.com/apple/swift-collections/blob/main/Sources/DequeModule/RigidDeque/RigidDeque.swift).

**Keep Igor's eight selected tools.** Scope Kingfisher to images/thumbnails, Maestro to a few supported UI flows, and SwiftLint/formatting to one shared configuration. Skip Nuke while Kingfisher is the choice. Keep Tuist deferred unless measured build or project-management costs exceed what XcodeGen handles. Keep Swift Testing and XcodeGen as existing foundations if “already in use” is accurate; adoption of something already deployed has no incremental savings.

**GRDB: conditional, with an explicit migration and sync design.** It is a good SQL toolkit, but “fallback if SwiftData fights you” understates schema migration, observation changes, data recovery, and sync ownership. Replacing storage is a project, not a library swap. Retain it for a demonstrated query or persistence problem. [GRDB](https://github.com/groue/GRDB.swift).

**KeychainAccess: replace the rationale, not automatically the library.** An old last-push date alone is insufficient evidence that a stable wrapper should be discarded. A tiny Security-framework adapter can be appropriate for one narrow credential type, but “30 lines” ignores accessibility classes, access groups, updates, errors, and migration. Keep an existing working wrapper unless compatibility or maintenance evidence warrants replacement; test its locked-device behavior. [KeychainAccess API and accessibility examples](https://github.com/kishikawakatsumi/KeychainAccess).

**Sentry and Firebase: defer by need, not by asserting equivalence with bug-kit.** bug-kit documents local reports, session logs, MetricKit diagnostics, crash files, and device collection. That fits Igor's personal device loop well. It does not establish equivalence to a hosted fleet-observability service. [bug-kit](https://github.com/idvorkin/bug-kit). Sentry's SDK supports crash/error and performance reporting; revisit it if external testers create a collection, symbolication, or release-triage gap. [Sentry Cocoa](https://github.com/getsentry/sentry-cocoa). Firebase lets developers select products, so “the SDK is heavy” is too coarse; evaluate the actual selected product graph and collection behavior. There is still no stated need to add it now. [Firebase setup](https://firebase.google.com/docs/ios/setup).

The savings column currently mixes benefits, prerequisites, and unsupported causal claims. ## 4. A cheap TCA conversion-cost spike

**Run one bounded comparison; budget four hours of implementation elapsed time plus 45 minutes of Igor's review.** These are suggested experiment limits, not estimates that the conversion will fit. Stop and report unfinished work when the budget is exhausted. Do not convert bug-kit or a whole app to justify a successful demo.

Choose a real Context Grabber journal list/search feature with async loading, a loading/error state, debounce, cancellation, and a detail sheet. If that exact feature does not exist, choose the nearest existing slice with comparable effects. A static What's New screen is too easy to reveal integration cost; the live camera/CoreML pipeline is too expensive for this first question.

1. **Freeze behavior before conversion.** Write a short acceptance checklist from the existing feature and capture a baseline log trace. Include success, failure/retry, rapidly changing queries with out-of-order results, dismissal while work is pending, and reopen. Define expected cancellation and late-result behavior explicitly. Preserve the same user-visible UI and bug-kit event names.
2. **Extract shared boundaries once.** Use the same small client interfaces, fixtures, clock, IDs, and logging sink in both variants. Record extraction time separately: it benefits the current architecture too. Keep Apple adapters and persistence implementation unchanged. Plain Swift logic must remain runnable with host tests.
3. **Compare two variants from the same baseline.** A: the existing Observation/view-model approach with those clients and tests. B: one TCA feature using current APIs from the pinned release, its Store/reducer, and TestStore. Include the parent presentation boundary and clean cancellation; do not hide bridging work in “later.” Use the same agent/model settings and acceptance checklist, working sequentially. Track learning/setup separately from conversion. This is a practical comparison, not a statistically controlled productivity study.
4. **Exercise the same behavior.** Run host tests first. Then use one shared simulator lock and an explicit destination for UI checks, with parallel simulator testing disabled. Finally build and install through the existing `xcodebuild`/`devicectl` path and compare the resulting logs. Record target compilation for iOS, watchOS, and Mac where applicable; compiling a target is separate from claiming hardware validation.
5. **Make one follow-up change in both variants.** For example, preserve the old results during refresh and prevent a cancelled request from overwriting them. This exposes whether the new structure makes the next agent change cheaper. Deliberately introduce one stale-response bug and verify that each suite catches it; an impressive test count alone is weak evidence.

| Measure             | What to record                                                                                                                                                                             |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Conversion effort   | Shared extraction, TCA-only work, integration fixes, documentation, and review as separate time buckets; agent wall time/cost separately from human minutes.                               |
| Change surface      | Production/test files and lines changed, new concepts, parent-screen edits, and modifications outside the chosen feature. LOC is context, not the score.                                   |
| Agent friction      | Compile/test repair iterations, obsolete API attempts, and Igor interventions.                                                                                                             |
| Build/test overhead | Dependency resolution separately from cold build; a few identical warm incremental builds and host-test runs on the same machine/toolchain. Note macro compilation and added dependencies. |
| Behavioral evidence | Acceptance cases passed, pending effects correctly cancelled, stale-result bug detected, and preserved diagnostic events.                                                                  |
| Ongoing cost        | Time and review effort for the identical follow-up change; clarity of the explanation a fresh session needs.                                                                               |
| Reversibility       | Can the slice be removed without changing the shared domain or forcing neighboring features into TCA?                                                                                      |

A reasonable provisional go/no-go rule: **all acceptance cases pass; conversion stays within the timebox and feature boundary; Igor can review it within the review budget; warm edit/test time does not regress by more than 20%; and the follow-up change or debugging evidence shows a concrete advantage over A.** The 20% threshold is a proposed tolerance, not a TCA performance claim. A tie favors the current architecture. A failure to finish is useful conversion-cost evidence, not a reason to silently enlarge the spike.

For extrapolation, classify remaining features as simple state/UI, async orchestration, or hardware/persistence-heavy. Report a range for each and explicitly mark categories the spike did not sample. Do not multiply converted lines of code across the repository. A rough break-even calculation is `one-time conversion/review effort ÷ recurring effort saved per comparable change`, using the same units and including upkeep. If the observed recurring saving is zero or negative, there is no measured break-even.

My prior is that **injected clients plus controllable clocks will deliver much of Igor's immediate benefit**. TCA may additionally help agents follow consistent state/effect conventions in complicated orchestration, but the spike should demonstrate that incremental benefit. Keep high-frequency frames, pixel buffers, and inference processing in dedicated services; expose coarse events and summaries to feature state. If one slice wins, adopt there and reassess after several real changes rather than declaring an app-wide migration.
